# Internationalisation — Admin-Managed Locales

**English is the default and the source language.** Every other locale is added, translated,
and published from the admin panel without a developer, a deploy, or a code change. The
system is designed for up to **seven active locales**.

Nothing about a locale is hard-coded. There is no array of language codes in the source.
A locale is a database row.

## 1. The two kinds of translatable text

Conflating these is the mistake that makes multilingual sites unmaintainable. They have
different owners, different editors, and different workflows.

| | **Content** | **UI strings** |
| --- | --- | --- |
| Examples | Hotel names, descriptions, offer terms, page bodies, image alt text | Buttons, labels, validation messages, emails, error text |
| Keys defined by | Content editors, as they create entities | Developers, in code |
| Stored in | Translation tables (`HotelTranslation`, …) | `TranslationString` table |
| Edited in | The entity's own admin screen, side by side with English | The Translation Manager |
| Volume | Grows with the catalogue | ~600–900 keys, grows slowly |

Both resolve through the same locale registry and the same fallback chain, so a guest never
sees a mixture of languages for reasons they can perceive.

## 2. The locale registry

```
Locale
──────
code              'en' | 'ar' | 'de' | 'ru' | 'fr' | 'it' | 'es'   (BCP 47)
name              English name            — "German"
native_name       Endonym                 — "Deutsch"
direction         'ltr' | 'rtl'
is_default        exactly one row is true
is_enabled        visible on the public site
fallback_code     FK → Locale.code, nullable (null → default)
display_order     order in the language switcher
script            'latin' | 'arabic' | 'cyrillic' | …   → drives font subsetting
date_format       Intl options override, nullable
number_format     Intl options override, nullable
created_at
```

`is_default` is English and is protected: it cannot be disabled, deleted, or have its
translations emptied, because it is the fallback of last resort and the source every other
locale is translated from.

`direction` is per locale, so RTL is a property of the data rather than a special case for
Arabic. Adding Hebrew, Persian, or Urdu later needs no layout work — the RTL system built
for Arabic already covers them. All component CSS keys off `[dir="rtl"]`, never off
`[lang="ar"]`.

`script` matters more than it looks: it drives which font subsets are preloaded. Seven
locales across Latin, Arabic, and Cyrillic must never mean a visitor downloads all three.

### Suggested seven for the Egyptian market

English (default) · Arabic · German · Russian · French · Italian · Spanish — the largest
inbound tourism source markets. The set is configuration; this is a starting point, not a
constraint.

## 3. UI strings

```
TranslationString
─────────────────
id
namespace         'common' | 'booking' | 'search' | 'admin' | 'email' | …
key               'booking.checkout.confirm_and_pay'
locale_code       FK → Locale
value             the translated text (ICU MessageFormat)
status            'missing' | 'machine' | 'draft' | 'translated' | 'needs_review'
source_hash       hash of the English value this was translated from
translated_by     FK → User, nullable
updated_at
UNIQUE (namespace, key, locale_code)
```

### Keys come from code; translations come from the database

Developers define keys in the English catalogue in the repository. On every deploy a sync
task reconciles that catalogue with the database:

- **New key** → a row is created for every locale, `status: 'missing'`.
- **English value changed** → `source_hash` no longer matches, so every non-English row
  flips to `needs_review` and keeps its old value. The site keeps working; the Translation
  Manager shows exactly what drifted.
- **Key removed from code** → the row is soft-deleted, never hard-deleted, so a rename does
  not destroy paid translation work.

This is the property that keeps a seven-language site honest. Without `source_hash`, changing
an English sentence silently leaves six languages saying something else, and nobody finds out.

### Resolution and fallback

```
requested locale → locale.fallback_code → default locale ('en') → the key itself
```

A missing string renders in English, never as `booking.checkout.confirm_and_pay`. In
non-production environments missing keys are visibly flagged in the UI so they get caught
before launch rather than by a guest.

### Delivery

Catalogues are **compiled, not queried per request**. A publish action, or any string edit,
rebuilds that locale's JSON bundle into Redis and purges the CDN tag. Next.js loads one
compiled bundle for the active locale.

Cost: one Redis read per render, and the app never touches the database for UI text. A
visitor browsing in German downloads the German bundle and nothing else — seven locales cost
the same on the wire as one.

## 4. Content translations

Every translatable entity has a translation table keyed `(entity_id, locale_code)`, as set
out in `data-model.md`. Adding a locale creates no rows and no migration — rows appear as
content is translated.

**Editing:** each entity's admin screen has a locale tab strip. The English source is shown
alongside the field being translated, so a translator never works blind. A per-entity
completeness badge shows which locales are finished.

**Slugs are per locale** and independently editable, so `/de/hotels/nil-turm` and
`/en/hotels/nile-tower` both carry their own SEO value. An untranslated slug falls back to
the default locale's slug rather than 404-ing.

**Fallback for content is per field, not per entity.** A hotel with a translated name but an
untranslated description shows the translated name and the English description. Blanking the
whole page because one field is missing would be worse.

## 5. Adding a language from the admin panel

The complete flow, no developer involved:

1. **Add locale** — code, native name, direction, script, fallback, display order.
2. The system creates `TranslationString` rows for every key at `status: 'missing'`, and
   registers the locale for routing, sitemaps, and `hreflang`.
3. **Optional machine pre-fill** — a translation provider (DeepL or Google) pre-fills every
   missing string at `status: 'machine'`. Machine output is never treated as finished and is
   visually marked throughout the Translation Manager. For seven languages this converts an
   impossible task into a review task.
4. **Translate** — either in the Translation Manager, or by **exporting** to JSON, CSV, or
   XLIFF, sending it to an agency, and **importing** the returned file. Import is a dry-run
   diff first: added, changed, and conflicting rows are shown before anything is written.
5. **Translate content** — hotels, room types, offers, and pages via each entity's locale tab.
6. **Preview** — staff can browse the full site in the locale before it is public, via a
   signed preview cookie.
7. **Enable** — the locale appears in the language switcher, sitemap, and `hreflang` set.

### The publish gate

A locale cannot be enabled until it passes a configurable threshold — by default **100% of
UI strings** in a non-`missing`, non-`machine` state and **100% of published hotels and
destinations** translated. Admin shows exactly what is outstanding.

This gate exists because a half-translated site is worse than a single-language one. It
looks broken, it damages trust at the moment of payment, and Google will index the mixture.
The threshold is adjustable, and it can be overridden with an explicit, audited confirmation
— but never by accident.

## 6. Routing and SEO

**Every locale is prefixed, including the default:** `/en/…`, `/ar/…`, `/de/…`. A bare `/`
redirects to `/en`. Leaving the default unprefixed saves one path segment and costs
duplicate-content ambiguity, a special case in every URL helper, and a canonical problem
that grows with each locale added. With up to seven, consistency wins.

- `hreflang` alternates for every **enabled** locale on every page, plus
  `x-default` → English. Disabled locales never appear.
- One `sitemap-{locale}.xml` per enabled locale, in a sitemap index.
- Self-referencing canonical per locale.
- Language detection from `Accept-Language` **suggests** via a dismissible banner and never
  auto-redirects. Forced redirects break shared links and search-engine crawling.
- The choice is persisted in a cookie and, for staff, on the user record.
- The language switcher maps the current entity to its slug in the target locale, so
  switching from an English hotel page lands on the same hotel in German — not the homepage.
  This is the detail most multilingual sites get wrong.

## 7. Formatting

All formatting goes through `Intl` with the active locale: dates, times, relative times,
numbers, plurals, and lists. UI strings use **ICU MessageFormat**, so plurals and gender are
the translator's job rather than string concatenation in code.

**Numerals:** Western digits (0–9) in every locale including Arabic, because Egyptian
commerce and pricing use them and Eastern Arabic-Indic numerals slow price scanning in a
checkout. Prices always render with `tabular-nums`.

**Currency:** EGP is the settlement currency in every locale. If display conversion is added
later, the converted figure is indicative and the EGP total is always shown at payment.

## 8. Admin API

```http
GET    /api/v1/admin/locales
POST   /api/v1/admin/locales
PUT    /api/v1/admin/locales/{code}
POST   /api/v1/admin/locales/{code}/enable      # runs the publish gate
POST   /api/v1/admin/locales/{code}/disable
GET    /api/v1/admin/locales/{code}/completeness

GET    /api/v1/admin/translations?locale=&namespace=&status=&q=
PUT    /api/v1/admin/translations/{id}
POST   /api/v1/admin/translations/bulk
POST   /api/v1/admin/translations/machine-prefill
GET    /api/v1/admin/translations/export?locale=&format=json|csv|xliff
POST   /api/v1/admin/translations/import        # dry-run diff, then commit
POST   /api/v1/admin/translations/publish       # recompile bundle, purge CDN
```

Locale management is `SUPER_ADMIN` and `GROUP_ADMIN`. Translating is available to
`CONTENT_MANAGER`, and a dedicated `TRANSLATOR` role — scoped to translation only, with no
access to bookings, guests, or pricing — is added to the role set so agency users can be
given accounts safely.

## 9. Performance with seven locales

- One compiled bundle per locale; the active locale only, ~15–25KB gzipped.
- Fonts subset and preloaded **by script**, driven by `Locale.script`. A German visitor
  downloads Latin only; Arabic and Cyrillic faces are never requested.
- ISR caches are keyed by locale, and content publishing revalidates only affected locales.
- The sitemap index grows linearly; individual sitemaps stay small.
- Translation bundles are versioned by hash so a publish invalidates immediately without
  waiting for a TTL.
